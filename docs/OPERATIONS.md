# Operations and production readiness

## Deliberate scope

This application includes a working catalogue, account/address handling, persistent guest/customer selections, checkout reservation logic, real Razorpay API integration code, and protected administration. It has not been deployed as a live shop or verified with real gateway credentials. The included demo content is not real inventory.

## Required before live sales

- Use a **fresh MySQL production database**, core Flyway migrations only, no `demo` Spring profile and `DEMO_DATA=false`. Do not toggle the migration profile on a database already seeded with V2; migration validation intentionally detects missing applied migrations. Export/re-enter verified inventory into the clean production database.
- Upload real product photography (body, border, pallu and blouse as available); supply accurate material/weave/weight/dimensions/care details, verified prices and available stock. Remove demo catalogue records. No certification or authenticity claim is generated by the software.
- Replace contact placeholders; set the WhatsApp link with the real business number. Instagram currently points to the Haritha Vastra account supplied in the project context.
- Have shipping, returns/refunds, privacy and terms approved and replace the policy placeholders. Set dispatch/serviceability information. The app collects customer delivery data; establish retention/deletion and support procedures.
- Configure appropriate shipping/tax treatment. Current simple pricing is not a GST compliance, invoicing or accounting system.
- Deploy Spring to a JVM-capable host (e.g. your container server), managed/private MySQL and the frontend through HTTPS. Keep DB/admin ports private, define exact CORS origins, add a CSP compatible with your Razorpay checkout and image hosts, configure secure headers and do a security review.
- Add edge/application rate limits for registration, login, guest-token creation, checkout, payment verification and uploads. Add email verification, password-reset/recovery, session management UI and administrator MFA or SSO before public launch. Current opaque sessions expire in 12 hours and logout revokes the current token.
- Remove ADMIN_PASSWORD from runtime after initial bootstrap; the app only creates a missing admin and never promotes an existing customer. Use a controlled administrative workflow for subsequent role/password changes. Protect admin accounts and avoid shared credentials.
- Configure secret management, separate test/live credentials, Razorpay capture and signed webhooks. Complete provider onboarding. Test success/failure/cancel/pending/webhook outage/duplicate/late-capture scenarios with real test keys.
- Back up MySQL and uploaded images with restore drills. Store image uploads in durable shared object storage before running multiple backend instances; the supplied volume is appropriate for one local instance. Image uploads are decoded and re-encoded to strip extraneous content. Add thumbnail generation/CDN and orphan-image cleanup for larger catalogues.
- Monitor errors, inventory reservations, payment/receipt mismatches, `GATEWAY_ERROR` and `PAID_REVIEW`. Reconcile daily with Razorpay. Refunds and disputes are manual in the provider dashboard; refund lifecycle synchronization is not implemented.
- Apply supported dependency/security updates and scan images/dependencies before deployment. The package is pinned to a tested dependency set, not advertised as the latest releases.
- Run the real MySQL Testcontainers suite, browser/device/accessibility acceptance tests and a staging restore/payment rehearsal. Review logs to ensure they never expose card details, bearer tokens, API secrets or full delivery payloads.

## Inventory and transaction model

Cart mutations serialize on the owner cart row. Checkout locks product rows in ascending ID order. JPA transactions and database nonnegative-stock constraints prevent overselling. An order reserves stock once; capture does not deduct a second time. Expiry/cancellation releases once, and late capture attempts to reacquire all items atomically before marking paid. A captured payment with insufficient stock enters `PAID_REVIEW`; never fulfil it automatically.

Price and quantity are read from the server. Order items snapshot name, collection, image, unit price, original price and quantity. Order totals and delivery data are snapshotted. Idempotency keys are unique per owner. Gateway payment IDs and provider-order IDs are unique. Webhook event IDs are persisted, and current provider status is fetched to avoid stale-event regressions.

The reservation scheduler runs every minute and retains stock if gateway reconciliation fails. This favours correct accounting over premature resale. Check stale reservations and provider timeouts operationally. Gateway calls currently occur while an order transaction holds a lock; a durable outbox/queue is recommended before significant scale.

## Usability and account limits

Guest cart/wishlist access is browser-local through an unguessable bearer token. Clearing local storage loses the pointer to those guest records. Guest orders are not automatically claimed by a later account; implement verified-email recovery/linking if needed. Login merges shopping selections, not orders.

Search is database-backed substring search, suitable for a small shop. Rating aggregation currently fetches reviews per product; move to aggregate queries/materialized summaries and managed search when catalogue/review volume warrants it. Shipping carrier tracking, coupons, GST invoices, refunds, SMS/email notifications and password recovery are not integrated.

The demo colours/collections establish the starting catalogue. Admin-supplied products must use consistent collection and occasion labels. No native mobile application is included; the React application is responsive.
